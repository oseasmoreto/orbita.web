# App shell (`AppLayout`/`AppHeader`/`AppSidebar`/`useAppShell`)

## `router.back()` can escape the app entirely — always guard with `window.history.state?.back`
`router.back()` calls `window.history.go(-1)` under the hood, which operates on the browser's real session history, not a history scoped to the SPA's own navigation. On a tab with no prior in-app navigation (a fresh tab, or right after a full reload), "back" falls through to whatever the browser's real previous entry was — including a different origin/port entirely (confirmed: landed on a stale `localhost:5175` from an earlier dev-server session). `window.history.state?.back` is written by Vue Router's own `createWebHistory` on every SPA navigation (`{ back, current, forward, ... }`) and is `null`/falsy when there's no real in-app back-target — check it before calling `router.back()`; otherwise make the action a no-op rather than ever risking leaving the app.

## `position: sticky` only pins the axis you set — it does not protect against horizontal scroll desync
`AppHeader.vue`'s `position: sticky; top: 0;` only fixes the vertical axis. If the page has ANY horizontal scroll (even a few px, from something as unrelated as a third-party fixed element overflowing the viewport — see `.ai/rules/vue-sonner.md`) and the user has scrolled right even slightly, the sticky header shifts left along with that scroll while sibling `position: fixed` elements (the mobile drawer, its overlay) stay pinned to the viewport regardless — producing a visible seam/misalignment gap. The real fix is eliminating page-level horizontal scroll entirely (`overflow-x: hidden` on `html` only — see `.ai/rules/vue-sonner.md` for why never also `body`), not trying to make the header horizontally sticky too (`left: 0; right: 0;` would still leave visual artifacts if scroll position itself is nonzero when the drawer opens).

When verifying sticky behavior with Playwright, don't stop at `header.getBoundingClientRect().top === 0` after calling `scrollTo` — that assertion is vacuously true if the page never scrolled at all (see `.ai/rules/vue-sonner.md`'s `overflow-x: hidden` entry for exactly this false-positive that shipped once already). Always also assert `window.scrollY` actually changed first.

## `useAppShell()` is a module-level singleton, not per-call state — never re-declare its refs locally
`isMobileNavOpen`/`expandedItemIds`/`isNotificationPanelOpen`/`hasUnreadNotifications`/`isDesktopSidebarCollapsed` are declared once at module scope in `composables/useAppShell.ts`, outside the exported function — this is intentional (there's exactly one shell per app, and `AppHeader`'s hamburger button and `AppSidebar`'s drawer must observe the exact same open/closed state, not independent copies). Any new piece of shell-wide UI state (not domain state — this is UI-only, Pinia is for domain state, see `docs/infra/convencoes-frontend-infra.md` §5) goes here the same way, as a module-level `ref` plus an idempotent-safe mutator when a component might call it from `onMounted` on every remount (see `expandItem` vs `toggleItem` — `expandItem` intentionally never collapses, because a component set to "expand by default" would otherwise fight a user who already collapsed it and triggered a remount).

## The nav tree (`config/navigation.ts`) doubles as the breadcrumb's data source — don't hand-maintain a second copy
`composables/useBreadcrumb.ts` derives the header breadcrumb by searching the same `navGroups` tree that feeds the sidebar (`config/navigation.ts`), matching the current route by `to.name` — it does not read a separate `meta.breadcrumb` field or a hand-written trail. Adding a new sidebar item automatically gives it a correct breadcrumb for free as long as its `to` is set.

## Every new route needs a breadcrumb check — this has regressed 3 times already, don't let it be a 4th
A route with no matching entry in `navGroups` (by `to.name` or `relatedRouteNames`) doesn't error — it silently falls back to `route.meta.title` ALONE, dropping the whole ancestor trail (e.g. "Marketplaces do produto" instead of "Catálogo / Produtos / Marketplaces do produto"). This never throws, never fails a test, never shows up in typecheck/lint — the only way it's caught is someone actually looking at the rendered breadcrumb, which is exactly why it slipped through 3 separate times (`products-new`/`products-edit`, then again for `product-marketplaces` from a different module days later): a route that isn't itself a sidebar item's own `to` (a create/edit deep link, a nested detail route reached only via a row action or another view's button, anything whose real "home" in the nav tree is an ANCESTOR item, not itself) needs that ancestor item's `relatedRouteNames` extended to include it.

**Checklist for every new route added to any `modules/*/routes.ts`, no exception:**
1. Does this route's own `name` appear as some nav item's `to.name`? If yes, done — breadcrumb resolves for free.
2. If no (deep link, nested/child route, action-triggered navigation): find the nav item that represents its closest logical parent screen, add this route's `name` to that item's `relatedRouteNames` array in `config/navigation.ts`.
3. **Verify it in an actual browser, not just by reading the code** — load the route and read the rendered `.ui-breadcrumb` text. Don't trust that adding the array entry was enough; confirm the trail actually shows the full ancestor chain, not just the route's own title.
4. If the route's parent module is DIFFERENT from the route's own module (e.g. a Catalog screen navigating into a Pricing route), the `relatedRouteNames` entry still goes on the nav item of whichever module's sidebar entry is the logical parent — this crosses module boundaries in `navigation.ts` only, never as a file import between the two modules' own code.

## A route with a dynamic segment (`:id`) breaks "Recentes"/favoriting unless the param is carried along — same failure family as the breadcrumb one above
Reported by the user, 2026-08-31: clicking a "Recentes" sidebar entry for `product-marketplaces` (path `products/:id/marketplaces`) threw an UNCAUGHT `Error: Missing required param "id"` from vue-router's own `resolve()` — not a try/catch-able app error, it crashes the `RouterLink` render outright. Root cause: `router.afterEach` in `core/router/guards.ts` recorded `to: { name: to.name }` for "Recentes", dropping `to.params` — replaying that stored target later, for any route with a required dynamic segment, omits the param vue-router needs to resolve the path. Fixed by storing `to: { name: to.name, params: to.params }` instead — trivial once seen, easy to reintroduce if a future refactor of `recordVisit()`/`afterEach` rebuilds the `to` object without params again.

The identical failure class exists for the star-icon "favoritar página atual" (`AppHeader.vue`) — but `UserFavoriteResource` (backend) only ever persists `route_name`, no params, so there's no equivalent fix by "carrying the param along": a favorited `products-edit`/`product-marketplaces` could never resolve back to a specific record anyway. Instead, favoriting is disabled outright for any route with a resolved param (`isCurrentRouteFavoritable` checks `Object.keys(route.params).length === 0`), and the sidebar's favorites list defensively filters out any already-persisted favorite whose route requires a param (`AppSidebarContent.vue`'s `routeRequiresParams()`, checking the matched route record's `path` for `:`) — covers a favorite created before this fix existed, without needing a backend migration.

**Whenever a new route is added with a dynamic segment (`:id`, `:slug`, etc.), check both:**
1. Does anything feed this route's `name` into "Recentes" (any `router.afterEach` tracking) with a hand-built `to` object? If so, it must carry `params`, not just `name`.
2. Is this route reachable from the "favoritar página atual" star button? If it has a required param, it must be excluded from `isCurrentRouteFavoritable` (or wherever the equivalent check lives) — a route with a param can't be meaningfully favorited under the current backend contract (name-only), so don't let it silently create a favorite that will crash the sidebar the next time someone opens it.
