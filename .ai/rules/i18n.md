# i18n (`core/i18n/messages/pt-BR.ts`)

## No loose UI text in a `.vue` — ever, not even a single hardcoded label
Explicit, repeated instruction from the project owner (2026-08-28) after finding several hardcoded strings in `HomeView.vue` (headings, `StatCard` labels, `ChartCard` titles, `DataTableColumn` titles) even though `vue-i18n` was already wired up in the project — it had only ever been used for resolving backend-driven `ApiMessageKey`/`NotificationMessageKey` (`useApiMessage.ts`), never for general UI copy. The scope is now explicit and total: every heading, label, column title, button/action text, or placeholder is a key in `core/i18n/messages/pt-BR.ts`, resolved via `$t()` in the template or `useI18n().t()` in `<script setup>` — never a literal string.

Two mechanically different call sites need two different resolvers:
- Anything written directly in `<template>` (headings, static prop values): `$t('namespace.key')` — no import needed, `vue-i18n`'s global injection makes it available.
- Anything built in `<script setup>` that isn't template markup (a `DataTableColumn[]`, a `DropdownMenuOption[]`, a `ChartMetricOption[]`, any array/object assembled before the template renders): `const { t } = useI18n()`, then `t('namespace.key')` — `$t` does not exist outside the template.

## `common` namespace first — check it before adding a page-scoped key
Also explicit, same session: text that isn't specific to one module/page — a generic row action (`editar`/`excluir`/`visualizar`/`baixar`/`ações`), a marketplace name (`Shopee`/`TikTok`/`Amazon`/`Mercado Livre`/`Magalu`/`Outros`) — lives in `common`, not duplicated inside each page's own namespace. `HomeView.vue`'s dashboard consumes `common.actions.*`/`common.marketplaces.*` for exactly this reason: the same row-action labels and marketplace names will recur in the CRUD example and every future module, and the catalog should have exactly one source for each, not one per page that happens to need it. Before adding a new key anywhere, grep `common` in `pt-BR.ts` first — a key that's about to be duplicated across two page namespaces almost always belongs in `common` instead.

## The rule applies to `.ts` files too, not just `.vue` templates
Caught by the project owner, 2026-08-28: `modules/catalog/routes.ts` had `meta: { title: 'Produtos' }` — a raw hardcoded string in a plain `.ts` file, the exact same violation as a literal in a `.vue` template, just easier to miss because it isn't inside a `<template>`/`<script setup>` block being visually scanned for i18n compliance. `route.meta.title` (declared in `core/router/guards.ts`) is now documented as holding an **i18n key** (e.g. `'catalog.products.title'`), never resolved text — every `routes.ts` across every module follows this, and a route's title always reuses the page's own existing key (`catalog.products.title` is shared by the route meta, the browser tab title, and the page's own view) rather than duplicating the string under a second key.
- Resolving a key **outside** any component (a router guard, a Pinia store, any plain module-level `.ts`) uses the exported `i18n` singleton directly: `i18n.global.t('namespace.key')` (`core/router/guards.ts` does this for `document.title`, since `router.afterEach` never runs inside `setup()`).
- Resolving a key **inside** a composable/component still uses `useI18n().t()` — `useBreadcrumb.ts` resolves `route.meta.title` this way before handing it to the pure/testable `resolveBreadcrumbItems()`.
- Same principle already applies to Zod form schemas (`modules/catalog/schemas/productFormSchema.ts`): validation messages are UI text too, so the schema is a **factory function** (`createProductFormSchema(t: (key: string) => string)`), never a static object with a hardcoded message — the composable that owns a real `useI18n()` (`useProductForm.ts`) calls the factory, tests call it with `(key) => key` instead of mounting `vue-i18n`.

## A literal `@` in a message string silently breaks rendering — escape it
Found building the Identity screens (login/register/forgot-password, 2026-08-28): `identity.login.placeholders.email: 'seuemail@exemplo.com'` compiled to a runtime `SyntaxError` ("Invalid linked format") from `@intlify/message-compiler` — `@` is vue-i18n's own special character for **linked messages** (`@:key`/`@.modifier:key`, a message referencing another key), so any literal `@` in a message string is parsed as the start of that syntax, not as text. The failure is easy to miss: it throws as an unhandled render error on the specific component using that key, not a build-time or lint error, and the visible symptom looks like "a form field/section is just missing from the DOM," not an obvious i18n error.
- **Fix**: escape it with a backslash in the message VALUE — `'seuemail\\@exemplo.com'` in the `.ts` source (the doubled backslash is TypeScript's own string-escaping; the actual runtime string is `seuemail\@exemplo.com`, which `@intlify/message-compiler`'s `TEXT_ESCAPES` regex (`/\\([\\@{}|])/g`) un-escapes back to a literal `@` at render time).
- **Wrapping it in single quotes (`'seuemail{'@'}exemplo.com'` or `"seuemail'@'exemplo.com"`) does NOT work** — that's ICU MessageFormat-style escaping, not what this compiler implements; it still throws the same `Invalid linked format` error. Confirmed by testing both against the actual failure before landing on the backslash form.
- Same escape applies to the other special characters in message text: `\\`, `\{`, `\}`, `\|` — any literal occurrence of those four characters (backslash, brace, brace, pipe) plus `@` needs this treatment, not just `@`.

## Domain data is not UI copy — don't force it through a translation key
A product name from the API, a formatted price (`"R$ 59,90"`), a date (`"12/08/2026"`), a percentage (`"+12%"`) are content the app displays, not copy the app authored — they don't get an i18n key, no matter how tempting it is to be consistent. Forcing these into the catalog would blur the actual distinction the rule protects: `pt-BR.ts` is "text this product decided to say," not "every string that happens to appear on screen." `HomeView.vue`'s placeholder marketplace names (`marketplace.shopee`, etc.) are the one deliberate exception — they're UI-authored placeholder data standing in for a real `MARKETPLACE.name` from the backend (Fase 4 gap, not implemented yet), reused across the dashboard's chart labels and table rows specifically so there's one source instead of three copies of the same literal string; once real API data flows, those values stop being i18n keys and become actual response data.
